# Registering an Account and Using an Access Code

> [!note] Study notes based on the owner's Covered California training recordings. Original explanations; not affiliated with or endorsed by any organisation.

## What you will be able to do

- Say what you can still do for a consumer whose account has never been registered.
- Walk a consumer from the sign-in page to the account setup, in the right order.
- Explain what an access code does, where one comes from, and why the examples the training read out are not a table to memorise.
- Handle the setup prompts, including the one that asks how the programme should reach the consumer.
- Read an account that has just been created and say what it can and cannot tell you.
- Guide a consumer through the account creation page, and know what an invalid access code message is really about.

## Stage 1: An unregistered account is still workable

Everything in this lesson comes from one call, in which a consumer had never registered an online account. The instructive part was the walkthrough the representative gave while the consumer worked on their own phone.

Begin with the constraint, because it decides how the call goes. There was no account, and the representative had nowhere to post instructions because the email address on the record was not usable. What was on offer instead was three things: written instructions, a walkthrough on the phone at whatever pace the consumer wanted, and a callback later if the consumer hit a snag. None of that required an account to exist first, and that is the whole point — an unregistered account is a starting condition, not a dead end.

The representative was also explicit about the division of labour. The consumer held the phone and pressed the buttons; the representative named the next step and waited. So your role here is a guide rather than an operator. Nothing in the session shows a representative typing a consumer's details into a consumer's account.

The official record backs this up in its own words. The site asks you to confirm you are on coveredca.com, the official website, when you are helping someone enrol or manage an account, and to share personal information only with people you know and trust.

**The analogy.** It is like reading directions to someone who is driving. You cannot reach the wheel and you should not try, but you know the route and they can see the road. Naming the next turn is the entire job.

## Stage 2: The route through the site

Here is the route the training walked the consumer through, in order.

| Order | What happens                                                                                    | Who acts |
| ----- | ----------------------------------------------------------------------------------------------- | -------- |
| 1     | Open coveredca.com and find the sign-in area                                                    | Consumer |
| 2     | Choose the sign-in option, which reveals the sign-in fields and the option to create an account | Consumer |
| 3     | Choose to create an account                                                                     | Consumer |
| 4     | Answer Yes when the site asks about an access code                                              | Consumer |
| 5     | Enter the access code, then work through the setup prompts                                      | Consumer |

The step that catches people is step 2. Choosing the sign-in option does not make an account. What it does is show the sign-in fields alongside the route to creating one, so the consumer can see both and pick.

There is one honest wrinkle here. The training's recording describes the question the site asks at step 4 as being about the access code, and the consumer answered Yes. The official site's published description of the same journey puts a different Yes-or-No question in that place — the site's own words ask whether you have an application to link — and the answer there is also Yes. Do not script the wording of that screen from memory. What the two sources agree on is that the answer to the question on that screen is Yes.

## Stage 3: The access code

The access code is the thing that ties a new account to the application that already exists. Without it the consumer would have made an empty account, and would still have no way of reaching the records they came for.

Where one comes from is set out on the official site. A mailed notice carries it, and that notice goes out once the application has been submitted. And if a consumer does not have one, the site says to call the Service Center on (800) 300-1506, where a representative can generate a new one.

Now the trap, and it is a trap about the recording rather than about the site. The training read the code out character by character, giving a letter and a name for each character so that the consumer could hear letters and digits apart. But the transcript does not preserve that reading reliably. One letter is given two different names inside the same code, and another letter is attached to a name that does not begin with it. The code in the recording has five characters; nothing in the recording says that every access code has five characters, or that codes are made of letters only.

So do not memorise a table of letter-and-name pairs. Read the code exactly as the consumer gives it, and have them read it back to you before they type it.

## Stage 4: The setup prompts

Once the code is in, the site runs a series of prompts. The shape of the recording here is unusual and worth describing honestly: the transcript preserves a long run of prompts being answered Yes, one after another, without preserving what any individual prompt asked.

What that means is that the number of prompts is established and their wording is not. You can tell a consumer that there will be a run of screens to work through and that each one is answered Yes to continue. You cannot reconstruct the screens themselves from this recording, and you should not pretend to.

Two things inside that run are established well enough to act on.

The first is a warning about sensitive numbers. Twice the transcript contains the phrase your social, which in context is a warning to keep a Social Security number out of a prompt. Because the recording's wording is uncertain, treat it as a rule rather than as a quotation: do not type a Social Security number into a setup prompt, and if a prompt appears to be asking for one, stop and establish what it is before typing anything.

The second is the choice of contact method. At one point the consumer is asked whether the programme should reach them by email or by mail, and the consumer picks. That choice is worth taking properly, because the official site says documents such as tax forms are delivered both ways — posted to the address on file and placed in the online mailbox, with an email or a text when they are ready — and that a consumer can change how they receive communications in the account.

## Stage 5: Reading the account afterwards

At the end of the session the representative reviewed the new account with the consumer, and three things came out of it.

The first is a status the recording renders only loosely. It looked as though the steps for 2026 had been completed, and the Medi-Cal part was still pending, with the stated reason being that household income for the year had been reported at zero.

The second is the reason that status needs care. A second record on the same application showed employment income of $45,000 running from January through December at an employer the recording names as Dignity Health — the exact employer name is worth confirming on the record rather than trusting to the transcript. So the account carried a zero-income figure and a $45,000 figure at the same time, and the pending Medi-Cal status was resting on the zero. The recording does not show that conflict being resolved, and it should not be presented as resolved.

The third is the difference between a status and a decision. Pending is pending. It is not a denial, and it is not a determination that the consumer qualifies.

**Worked example.** You review a freshly created account with a consumer. One line says the Medi-Cal application is pending because income for the year was reported at zero. Another line shows $45,000 of employment income for January through December. The right move is to read both lines out, say plainly that the two do not agree, and ask the consumer which one is right — not to pick one for them, and not to describe the pending line as a result.

## Stage 6: Helping a consumer create the account

The earlier stages got the consumer as far as the account setup. This stage is what happens on the page itself, and it comes from a different session. There the walkthrough went field by field, and it spent most of its time on a message consumers misread.

Before anything else, there is one check to make. Before an access code is handed over, the case is read for a note from the county office saying that the case is not to be helped with an online account. The recording names the places to look: the case history, then the case summary and the notes. A household split across the two programmes — the official record's term is a mixed-program family, and the recording's own phrase was a mixed household — can still be helped with an online account. What decides the question is the note, not the shape of the household, and the note belongs to the county rather than to you. Your job is only to find out whether one has been left. If it has, the consumer is pointed at the county. If it has not, the help goes ahead. And when it has, it reaches the Covered California members of the household as well, not only the Medi-Cal member: a consumer who wants an account only to end their own coverage is still held by the county's note.

Then the fields, and the recording's rule is short. It is the whole of the instruction.

| Field on the page           | What goes in it                                                          |
| --------------------------- | ------------------------------------------------------------------------ |
| First and last name         | The first and last name the application carries, character for character |
| Date of birth               | The date of birth the application holds                                  |
| Social Security number      | Nothing; the field is skipped                                            |
| Preferred method of contact | Mail                                                                     |
| Mailing address             | The mailing address on the application, including any apartment number   |
| Other ways to be contacted  | No                                                                       |
| Username, password and PIN  | The consumer's own, chosen by the consumer                               |

Stage 4 covers the Social Security number rule. What this session adds is that the field is left empty and the rest of the form is filled to match.

One point is more specific here than in Stage 4. There the consumer chose between email and mail. Here the guidance is to pick mail, and to answer no to being contacted in other ways, with the reason given that an email address or phone number entered here may already belong to an account the consumer set up before, and that brings back the same refusal.

Now the trap, and it is why the session dwelled on this. The screen can return an invalid access code message for a code that is perfectly correct, because the message is about the way the page has been filled in rather than about the code. The recording demonstrated it: a birth date was altered by a few characters, the screen refused the code, and a second code generated afresh was refused in exactly the same way. The refusal follows the consumer through several fields — a name that differs from the one the application carries, a birth date that differs, a mailing address that is the newer one rather than the one on file, an apartment number left out — and any one of them is enough on its own.

That list is why the rule is to use the application's details and not the consumer's memory of them. The consumer has a good reason to type the newer information. Someone who has married and has not yet updated the application will put in the new name; someone who has moved will put in the new address. Both produce the same refusal as a typo would, and the consumer cannot see the difference. The way out is not to guess. The details can be corrected once the account exists: the recording's own example was to open the account with the name the application carries and then correct the application afterwards, and the same goes for an address that has gone stale — the old address goes in first and the new one is put on the record once the account is there.

Two lines the recording will not bend. The first is who types. No agent builds the consumer's online account for them, and the recording was blunt about why: doing it is a privacy violation, including the version where the consumer is put on hold while the agent builds the account and then resets the password so that the agent no longer holds it. The reason offered is practical as well as principled — the agent cannot see the consumer's screen, so the agent does not know what the consumer is doing wrong. You guide; the consumer enters.

The second is when to stop. After two or three attempts the recording says to send the consumer to an in-person agent, because on the phone you cannot watch the screen being worked through and cannot point at the field that is wrong. Offering the help is part of the job, and the offer does not include taking the account over.

**Worked example.** A consumer calls and wants an account so that they can see their plan. They give you their details, and as you read the form back they correct the birth date and give you their new address. The screen refuses the code again. Start with the check: read the case history, the case summary and the notes for a county note, because that decides whether the help goes ahead at all. Then take the details from the application rather than from the conversation — the name as the application carries it, the birth date as it is held, the mailing address on file with the apartment number included, mail as the preferred way to be reached, and no to any other ways to be contacted. Say plainly why, so that the consumer does not think the code is wrong. And do not reach for the keyboard.

## Review

Close this lesson and write down, from memory:

1. What you can still do for a consumer whose account has never been registered.
2. The five steps from the site to the account setup, and what each one does.
3. What an access code does, where a consumer gets one, and where the official record differs from the recording.
4. What the training established about the setup prompts, and what it did not establish.
5. The two figures the account review turned up, and why a pending status is not a decision.
6. What the account creation page asks for, why an invalid access code message can be about the details rather than the code, and why the account is never taken over from the consumer.

Then check the areas people consistently miss: that choosing the sign-in option reveals the route to creating an account rather than creating one, that the letter-and-name pairs are not a table worth memorising, that the account was carrying two income figures at the same time, and that an invalid access code message is about the details on the page rather than the code.
