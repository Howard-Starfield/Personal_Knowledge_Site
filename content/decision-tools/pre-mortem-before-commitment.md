A pre-mortem starts with an uncomfortable prompt: the plan failed, and the
team now has to explain why. Working backward from that result can expose risks
that sound impolite or premature during ordinary planning.

> [!abstract] Example content
> This is original mock material. The scenario and checklist exist to exercise
> article layout, callouts, tables, and links.

## Make the failure concrete

Use a specific failed outcome. "The project went badly" produces vague risks.
"The course launched, but readers stopped after the first lesson and the owner
could not tell why" gives the group something it can inspect.

Ask each participant to write possible causes before the group discusses them.
The goal is not a long risk list. The goal is to find causes that are both
plausible and detectable.

## Turn each cause into a test

| Possible cause                         | Early warning signal                        | Preventive action                        |
| -------------------------------------- | ------------------------------------------- | ---------------------------------------- |
| The first lesson assumes missing terms | Readers search for basic definitions        | Add a prerequisite note or glossary link |
| The course order hides the useful part | Readers jump to later lessons               | Move the practical example earlier       |
| Feedback has no clear destination      | The same question appears in several places | Give each question one review location   |
| The plan is too large to reverse       | Small changes require unrelated migrations  | Split the commitment into bounded trials |

An early warning signal must be observable. "Users become confused" is hard to
act on. A repeated search, abandoned step, or recurring question gives you a
specific place to investigate.

## Keep the review tied to the decision

The pre-mortem does not replace a decision record. It challenges one. Return to
[[decision-tools/write-the-decision-before-the-meeting|Write the decision before the meeting]] and add the strongest failure mode to its uncertainty section.

> [!question] Follow-up
> Which warning signal would appear early enough to change the plan without
> wasting the work already completed?
